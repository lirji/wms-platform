# 履约到出库的授权消息

当前切片已实现并通过定向集成验证，包括首次授权前取消和授权后的原状态重放。它不替代正式TM/RM协调和真实TC运行验收。

## 原始事实和兼容边界

新履约创建可传`ownerId`；运行消息启用时必须提供。货主与原订单行、数量、单位、保质期条件、策略版本在同源重放时逐项核对，不能仅信任客户端自报摘要。旧NULL货主不猜测回填，也不能通过同源重放赋予新货主。消息关闭时旧无货主客户端保留兼容创建。

履约V016追加`owner_id`与`fulfillment_outbox.delivery_payload`；原`payload`和历史迁移不变。满足真实TC来源绑定、Committed持久化证据、全部原分支确认、当前活动attempt后，在ALLOCATED及原Outbox的同一本地事务固化V1仓级投递快照。新拥有货主的attempt若缺TC集群/应用/事务组或原分配业务键，整个屏障事务失败。已经请求取消但尚未形成快照的attempt需先处理原事务结果和补偿，不继续生成执行授权。快照提交是本次授权签发点，之后的取消请求不撤销已发事实，须通过独立执行/库存补偿协议处理；重复确认不回退原授权状态。

快照包含企业、仓、货主、履约单、分配/attempt/XID、全部固定参与仓的分支/资源/预占/路由代际/确认版本、本仓原业务订单行和数量/单位、完整TC来源与终态证据。授权键和TC引用由原始身份稳定生成。JSON边界严格验证版本、整数范围、数量精度与证据来源；未知版本、截断数值、错TC来源均拒绝。

## 真实投递与本库消费

- `${topicPrefix}.fulfillment.events`接收AllocationCompleted审计事件，不是执行授权入口。
- `${topicPrefix}.outbound.authorizations`只接受受信来源wms-fulfillment的OutboundOrderRequested/ExecutionAuthorizationRequested。
- 履约发布器每轮最多32项、20秒停止领取新项，逐条短事务领取，释放连接后等待Kafka确认。领取租约30秒，8次预算，指数退避和抖动；原事件ID、正文、授权键不变，陈旧代际不能完成新领取。
- Kafka确认后才写PUBLISHED，业务是否完成由出库库事务决定。发布状态落库失败可以重复投递，不能生成新事件规避原幂等身份。
- 出库V016追加完整屏障正文到本地TC证据。建单、证据、授权及Inbox DONE同事务；最后一步失败全部回滚。原订单货主及全部分配行必须一致，既有手工证据不能冒充完整消息证据。
- 授权消息先到时可依据同一完整快照幂等补建再授权。普通建单消息只建单和保存证据，不单独授予执行权。迟到建单不回退已授权/已作业状态。

消息健康覆盖发布器、消费者和处理器；积压与失败沿用已有有界指标。受审计Outbox重排记录实际投递快照摘要，不改变正文或降低代际；旧缺完整上下文事件拒绝直接重排，须核查原始事实并单独制定恢复方案。外部Kafka ACL仍须限制谁能发布可信Topic，配置存在不等于生产ACL已验收。
