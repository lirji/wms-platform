# 履约 TC 终态观察与恢复

本运行路径只读取 TC 持久化终态，不调用 TC Confirm/Cancel，不把 `Finished`、TM 内存状态或单仓确认当作整单提交。原始候选证据及官方源码依据见 [TC_TERMINAL_EVIDENCE.md](TC_TERMINAL_EVIDENCE.md)。候选触发器只在隔离测试中安装；应用启动不修改 TC 库，也不执行生产部署。

## 启用条件

`wms.tc.audit.enabled=true` 时创建专用审计适配器和 `allocationRecoverySweep` 执行器。必须配置独立 TC 环境/集群 ID、事务分组、MySQL JDBC URL 和受控凭据；TM 应用固定为 `wms-fulfillment`。审计账号由数据库仅授予对应集群 `terminal_evidence` 表的 SELECT，不能复用 TC 写账号。凭据不提交仓库。审计池最多 4 连接、获取 500ms、连接 500ms、单语句 1s、网络 1.5s；不访问履约业务表，不运行 Flyway。就绪检查最多每5秒验证一次同表SELECT权限；探针使用同一有界池。

TC 来源必须在 TM 绑定原 XID 的同一本地事务写入 `allocation_tc_binding`：企业、attempt、XID、启动代际、TC 集群、应用、事务分组。一个集群的 XID 只能绑定一个 attempt，包括跨企业。旧行缺失来源时保持待恢复并使任务明确失败，禁止按当前配置批量猜测回填。

未配置真实审计或业务数据库时，XXL 调用明确失败，不再返回零项成功。真实 TM 发起、库存 RM 服务入口、可靠仓确认及出库授权投递仍需后续接线；启用只读观察不等于完整分配业务已开放。

## 一致性与资源边界

恢复按企业运行，本实例最多 4 个并发企业、每企业 1 个扫描；触发频率限全局 8/s、每企业 2/s。每轮最多 20 项、20 秒，在途网络请求受独立 JDBC 超时约束。检查点按企业持久化，有版本条件更新；扫描到末尾后重置再轮询，避免前 100 个悬挂事务永久挡住后续项。

先关闭业务会话，再查询 TC。回写重新锁定 attempt 并核对 XID、启动代际、固定参与者摘要。观察、ALLOCATED、建单/执行授权 Outbox 和本项检查点同事务；最后写入失败全部回滚，下一轮重放该项。缺证据正常等待；来源不匹配、审计不可用和陈旧回写使调度失败，但不撤销已经提交的其他项。此类失败推进该项检查点，下个扫描周期再观察，避免单个历史坏项阻塞整页。多实例重复观察允许，业务幂等与检查点 CAS 防重复效果。

终态只接受 TC 9/11/13，分别为提交、回滚、超时回滚。证据 JSON 必须匹配原 XID 和状态；已有证据只能等值重放，非终态及矛盾终态不能覆盖。Outbox正常写入让数据库约束失败回滚整个事务，重复事件还需逐项核对原始操作键与JSON正文，不能由INSERT IGNORE吞掉约束或内容冲突。回滚证据不派发出库，但本路径不擅自完成退款、释放或创建新 attempt；TC 负责其二阶段，业务失败收敛继续沿恢复协议实施。

参与仓确认必须具备同一 XID、正分支 ID、动作资源、预占标识及正数确认版本。相同分支不能改绑其他预占或路由代际，已确认/取消不能回退。释放屏障还要求 attempt 是履约单当前活动尝试；已 ALLOCATED 的 Outbox 修复同样重新检查证据及全部参与者。观察状态不是另一套全局决定。

## 验证范围

`TcAuditRecoveryIT` 使用隔离 MySQL 和真实 Seata 2.6.0，验证 TC 终态持久化、清理后 Finished 的局限、TC 停止后的读取恢复、数据库 SELECT 权限与撤销恢复。参与仓确认由明确测试夹具提供，不能据此声称真实库存 RM 与出库消息已贯通。

另以真实业务库验证 25 个 attempt 的有界扫描/重启续跑、最后 Outbox 写入失败时整项回滚、旧代际返回、伪造无分支确认、改绑预占及改写终态拒绝。最终测试结果记录在交付进度中，不以本文存在替代运行证据。
