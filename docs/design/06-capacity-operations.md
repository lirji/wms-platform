# 容量模型、部署与运维实施规范

## 1. 容量口径

“京东级”是规模方向，无可用于本项目的已确认订单/扫描数据。下面给出可代入模型及明确标注的合成压测样例，不引用或声称掌握京东实际订单量。

| 符号 | 输入 | 单位 |
| --- | --- | --- |
| D | 全网日订单数 | 单/日 |
| L | 每单平均商品行 | 行/单 |
| P | 峰值秒流量/全天平均秒流量 | 倍 |
| W | 平均拆仓数 | 仓/单 |
| R | 含失败/重试的预占调用放大 | 倍 |
| A | 每商品行完整作业链平均库存事务数 | 次/行 |
| E | 每库存事务平均业务事件数 | 条/事务 |
| H | 最忙 Cell 占全网流量比例 | 0..1 |
| B | 单条流水实际含索引存储字节 | 字节/条 |
| V | 在线流水保留期 | 日 |

估算公式：订单峰值 q=D/86400×P；分配调用峰值 q×W×R；库存事务参考上界 q×L×A（仓内作业峰值可能与下单错峰，必须独立测量）；事件峰值 q×L×A×E；热点 Cell 事务=q×L×A×H。流水容量需用每事务实际流水条数 J：D×L×A×J×B×V，再加副本/备份/归档冗余。

纯合成示例：D=10,000,000、L=3、P=10、W=1.4、R=1.2、A=6、E=2、H=0.05，则 q≈1,157 单/秒、分配调用≈1,944 次/秒、库存事务≈20,833 次/秒、事件≈41,667 条/秒、热点 Cell≈1,042 次/秒。此例只验证计算模型，不是生产目标、京东数据或实测能力。实际 J/B/V 和请求分布留待填入。

序列号登记负载单独计算：启用序列号的件数×首次收货/转移/退货/报废动作率；不能只按 SKU 行数估算。Outbox、去重、索引与快照会放大存储，需实际采样页大小和行宽。

## 2. 非功能目标提案

以下目标待业务与运维签署，任何“达标”必须附测量环境和负载：

| 项目 | 提议目标/范围 | 备注 |
| --- | --- | --- |
| Cell 库存命令 | 服务端 p95<=200ms，p99<=500ms | 不含 PDA 网络/设备执行；在约定稳态峰值下 |
| 跨仓分配 | p95<=2s；超时转异步结果查询 | 健康依赖下；故障恢复单独衡量 |
| 查询投影延迟 | 健康状态 p99<=5s | 超过阈值标识陈旧；不能影响写校验 |
| 库存不变量 | 超分、重复入账、负库存为 0 | 所有故障验证中均适用 |
| 可用性 | 月度核心写入口 99.95% 候选 | 分母、计划维护、业务拒绝如何计入需签署 |
| 灾备 | 区域灾难 RTO<=60min、RPO<=5min 候选 | 可能丢失已确认数据，须业务批准并对账恢复；不能承诺 RPO=0 |
| 普通故障恢复 | TCC TRIED/消息/任务积压可追踪恢复 | 不设置自动超时释放以追求表面恢复时间 |

若业务要求任何已确认库存写入不可丢失，需将 RPO 提升至 0，并重新选择跨故障域同步提交与可用性取舍，不能以异步备份满足该承诺。

## 3. 压测实施矩阵

| 阶段 | 负载 | 必测指标/退出条件 |
| --- | --- | --- |
| 正确性 | 2 Cell、2 仓、单 SKU 100 件，200 个并发预占请求 | 成功量<=100；余额/预占/流水一致；非超时响应也需查最终结果 |
| 稳态 | 目标 50%/100%，各至少 30min 合成运行提案 | p95/p99、错误、数据库锁等待、连接、CPU、I/O、投影延迟 |
| 热点 | 高倾斜 SKU/库位与冷 SKU 同时存在 | 热点失败受控，正常仓/租户不被挤占 |
| 峰值 | 目标 150%，持续 10min 提案 | 拒绝/排队有界，库存不变量不破坏，恢复后积压可排空 |
| 故障 | 丢响应、数据库切换、Kafka 中断、协调器宕机、worker 换主 | 不重复入账；TCC会话/Fence/TRIED不丢；旧 owner 写被拒绝 |
| 恢复 | 故障结束后限速重放，前台继续目标负载 | 重放不会压垮数据库；最终追平并对账 |
| 扩容 | 执行器增减、仓路由迁移、查询投影重建 | 无重复遗漏；任务和 Outbox 随归属恢复 |

数据集覆盖多批次、临期、序列号、部分履约、冻结、跨仓和历史大表。记录种子、代码提交、组件版本、拓扑、资源、DDL/索引、并发曲线、直方图、差异计数。没有真实硬件环境的设备模拟结果单独标为 simulated。

## 4. 开发与生产拓扑

开发使用 dev-infra MySQL 8.4、Redis 7、Kafka 3.8.0、MinIO；项目独立 schema/user、topic/group、Redis prefix、bucket，不复用其他业务凭据。已存在 drools-demo 的 XXL-JOB 3.4.2 配置，但未确认共享运维授权；新增 WMS 调度部署方案应先纳入 dev-infra 规划，不直接占用其现有调度库。

两 Cell 本地集成建议独立 MySQL 实例或至少独立 datasource，以真正验证跨库隔离；多 schema 单实例只能证明逻辑隔离，不能证明故障隔离。共享 dev-infra 不做 kill、清表、删除 topic 等故障注入；破坏性验证必须使用本任务专属隔离资源。

生产按区域/Cell 部署无状态副本、MySQL 高可用、Kafka 多故障域、受控对象存储、调度高可用。Kubernetes 可作为生产编排候选，团队无运维能力时先用已有成熟平台，不为架构图强行新增。每 Cell 独立连接/线程/队列预算，全局服务也分域限流。

配置权威：静态应用配置随部署版本；路由由控制平面版本化发布；SKU 策略由业务数据库维护；秘密由凭据服务注入。不得同一键在环境变量和 Nacos 中存在不明确优先级。动态策略在一轮分配中固定版本；未知路由、权限或单位配置拒绝业务写入。

## 5. 缓存与检索

Redis 只承载可容忍陈旧的基础资料/查询加速。示例默认 TTL 60 秒、抖动 10%、空值 5 秒仅供开发；每类键确定最大陈旧期和容量后才能生产启用。key 包含企业、仓及必要权限 scope，不缓存权限已撤销后的敏感完整结果。

更新后通过可靠事件携带版本失效/刷新；旧查询回填用版本防护，不能仅“先写库再删缓存”宣称强一致。Redis 超时使用受限回源、请求合并及熔断，禁止全部并发请求直接回源。库存判断、权限撤销、效期限制始终校验权威状态。

ES 首期不部署。若后续多条件检索证明关系库投影不足，使用可重建索引、显式 mapping、稳定文档 ID、版本防乱序与删除墓碑，重建追平后切别名；查询索引不承担库存判断。

## 6. 监控、告警与处置

| 指标/事件 | 触发建议 | 首要处置 |
| --- | --- | --- |
| stock_invariant_violation_total | 任一新增 | 封锁受影响范围的新写，保留证据，核对流水；不全库停服 |
| tcc_tried_reservation_age | 超恢复预算 | 查Seata TC会话/分支及业务attempt，不人工直接释放 |
| outbox_oldest_age / pending_count | 超积压预算 | 检查 broker/ACL/毒消息，限速恢复 |
| projection_lag | 超陈旧阈值 | UI 标示延迟，核心写重校验；必要时限制报表 |
| job_lease_conflicts / quarantined_shards | 连续增长 | 查 worker 版本/长事务/资源耗尽，按 shard 恢复 |
| serial_ownership_conflicts | 任一新增 | 隔离序列号，核对源释放和目标接收事实 |
| device_unknown_age | 超设备业务预算 | 查询设备、暂停依赖任务、人工现场核实 |
| db_pool_wait / lock_wait / deadlock | 达容量阈值 | 限制热点/后台任务，检查锁顺序和执行计划 |

指标标签仅 env/cell/service/operation/result 等有界集合，订单号/序列号放脱敏日志和 trace，不进入高基数指标。审计记录 actor、权限范围、来源、原/新状态、原因及关联 operation。

## 7. 灰度、回退与灾备

上线顺序：兼容迁移 → 新消费者 → 暗流量投影校验 → 非关键仓只读/模拟 → 单仓真实闭环（需授权）→ 小范围跨仓 → 扩仓。负责人按平台/SRE/业务仓经理登记；任一库存不变量违例立即中止放量，延迟或失败率超过批准阈值按观察窗口中止。

功能开关按仓/企业生效，默认关闭新策略；开关修改留审计与版本，不改变未决TCC attempt的协议语义。代码回退必须保证 schema/事件兼容；已发运、已调整等业务效果通过补偿恢复。数据库收缩迁移在旧路径退出后另行审批执行。

恢复演练使用隔离目标：恢复数据库+日志到批准时间点 → 恢复路由和密钥依赖 → 校验TC会话/Fence/预占/XID映射/序列号归属 → 恢复未发 Outbox → 重放 inbox 可去重消息 → 重建查询投影 → 对账确认 → 再开放写入。若备份早于已发运事实，先核对设备/外部回执，不能直接接受重复发运。

记录实际 RTO/RPO、缺失事件、业务差异及人工步骤。生成备份成功和容器 health 均不等于恢复验收通过。

## 8. v0.3独立三服务容量与恢复增量

前述q×L×A仅估算库存事务量。每次入/出库实物动作还包含来源T1、库存T2、来源回执T3，另加permit创建/STARTED与Outbox/inbox开销；分别测量三服务TPS、连接、日志/存储和队列延迟，不能将一个库存事务预算当整条链路成本。端到端SLO覆盖来源受理至库存回执收敛，物理执行耗时另算。

容量压测新增三类偏斜：inbound突发到货、outbound大促波次、inventory热点SKU；停掉任一来源服务，其他服务应仍可处理合法独立业务，但受其未闭环permit占用的库存不得被错误释放。恢复须联合来源command/physical事实、inventory posting/permit、回执水位进行核对。三服务可独立发布，需验证N/N-1命令/结果兼容；数据库账号不能跨写，迁移按服务独立版本执行。

路由迁移及盘点冻结先排空三服务执行链路，不再只检查一个库存库事务。生产恢复基于各库可追溯的检查点向量和消息补齐，恢复来源库较旧备份时不得重发已在inventory过账或设备执行的动作。

## 9. Seata运行预算

新增TC高可用、持久化会话、事务分组映射与RM注册/认证；不是复用XXL调度库。跨仓Try与Confirm/Cancel各自计入库存数据库和Fence写入负载，监控TC重试、TRIED占用年龄和成功屏障延迟。迁移必须排空TCC，恢复需TC会话/各库存Fence/业务映射联合核对。版本锁和故障验证见09。
